# แผนพัฒนา: พยากรณ์ฝนรายชั่วโมงตามจังหวัด–อำเภอ–ตำบล

วันที่จัดทำ: 27 กันยายน 2026
สถานะ: ดำเนินการ Phase 0–2 แล้วเมื่อ 27 กันยายน 2026; Phase 3 ยังไม่เริ่ม

ผลที่ทำแล้ว: ทะเบียนพื้นที่ ปภ. แบบ local, API รายการพื้นที่แบบไล่ระดับ, endpoint พยากรณ์ 24/48 ชั่วโมง,
การตรวจ geocode, cache/โควตา guard, metrics, UI เลือกพื้นที่และกราฟรายชั่วโมง และ tests ที่เกี่ยวข้อง

ทะเบียนหลังตัดแถวซ้ำมี 77 จังหวัด, 928 อำเภอ/เขต และ 7,658 รหัสตำบล/แขวง ระบบสร้างรหัส parent
จากรหัสตำบล 6 หลักเพื่อเลี่ยงฟิลด์รหัสอำเภอผิดรูป 1 แถว ทดสอบสดกับ TMD ที่กรุงเทพมหานคร ชลบุรี
นครราชสีมา เชียงใหม่ ราชบุรี นครศรีธรรมราช และสงขลาแล้ว geocode ตรงครบ 7 จุด ยังไม่ถือเป็นการยืนยัน
coverage ครบทุกตำบล; พื้นที่ใด geocode ไม่ตรงจะไม่แสดงพยากรณ์

## 1. เป้าหมายและขอบเขต

ผู้ใช้เลือกจังหวัด แล้วเลือกอำเภอและตำบลเพิ่มเติมได้ ระบบแสดงปริมาณฝน **พยากรณ์รายชั่วโมง** ของระดับพื้นที่ที่เลือก พร้อมยอดสะสมช่วงเวลาที่แสดง เวลาของข้อมูล แหล่งที่มา และสถานะข้อมูล

ระยะแรกดึงข้อมูลเมื่อเลือกพื้นที่ (on demand) ไม่ดึงทุกอำเภอและตำบลทั่วประเทศล่วงหน้า ไม่ใช้ค่าพยากรณ์แทนฝนตรวจวัดจริงหรือประกาศเตือนภัย และไม่แปลงค่าของจุดอ้างอิงเป็นคำอ้างว่าเป็นค่าเฉลี่ยของทั้งพื้นที่

**นิยามที่ต้องแสดงใน UI:** “ฝนพยากรณ์ ณ จุดอ้างอิงของพื้นที่” สำหรับจังหวัด/อำเภอ/ตำบล เพราะ TMD คืนพิกัดหนึ่งจุดต่อชื่อสถานที่ที่ทดสอบ ไม่ใช่ค่าเฉลี่ยเชิงพื้นที่

## 2. หลักฐานความเป็นไปได้

- TMD NWP endpoint `GET /nwpapi/v1/forecast/location/hourly/place` รับ `province`, `amphoe`, `tambon` แบบไล่ระดับ; เลือก `fields=rain` และ `duration` สูงสุด 48 ชั่วโมงตาม[คู่มือ TMD](https://data.tmd.go.th/nwpapi/doc/apidoc/forecast_location.html) ตัวแปร `rain` เป็นมิลลิเมตรต่อชั่วโมง
- ทดสอบสดวันที่ 27 กันยายน 2026 ด้วย token ใน `.env` โดยไม่แสดง token: `นครปฐม`, `นครปฐม/สามพราน`, `นครปฐม/สามพราน/ไร่ขิง` ได้ HTTP 200 ทั้งหมด และตอบ `location.geocode` ตามระดับพื้นที่
- คำขอระดับตำบล `fields=rain&duration=24` คืน 24 ชั่วโมงครบ ตั้งแต่ `2026-09-27T20:00:00+07:00` ถึง `2026-09-28T19:00:00+07:00`; แต่ละชั่วโมงมีค่า `rain`
- Header โควตาระหว่างทดสอบแสดง limit 100,000 datapoints; หลังคำขอ 24 ชั่วโมงเหลือ 94,260 datapoints การใช้หนึ่งพื้นที่ × 24 ชั่วโมง × หนึ่ง field ลดโควตา 24 datapoints ไม่ทราบรอบรีเซ็ตที่แน่นอน จึงห้ามสมมติว่ารีเซ็ตรายวัน
- [คู่มือพื้นที่ TMD](https://data.tmd.go.th/nwpapi/doc/apidoc/forecast_area.html) มี endpoint แบบพื้นที่/ลุ่มน้ำ แต่ยังไม่ยืนยันว่าประหยัดโควตาหรือเหมาะกับรายการทุกตำบลกว่าการดึงแบบจุด จัดเป็นทางเลือกเพื่อทดสอบภายหลัง

## 4. แนวทาง API และข้อมูล

### 4.1 ทะเบียนพื้นที่

1. เลือกแหล่งทะเบียนจังหวัด–อำเภอ–ตำบลที่เชื่อถือได้ พร้อมรหัส ความสัมพันธ์ลำดับชั้น วันที่ข้อมูล และสิทธิ์ใช้ ก่อนนำเข้าโปรเจกต์
2. ตรวจชื่อที่ TMD รับจริง รวมชื่อซ้ำ คำนำหน้า `จ./อ./ต./เขต/แขวง` การเปลี่ยนชื่อ และพื้นที่ที่ TMD คืน `found: false` อย่าใช้ชื่ออย่างเดียวเป็น cache key
3. ให้ UI ส่งรหัสพื้นที่ที่เลือก; backend ตรวจ parent-child แล้วแปลงเป็นชื่อที่ TMD ต้องการ โดยอ้าง `province` เสมอ และใส่ `amphoe`/`tambon` ตามระดับ
4. หาก TMD คืน `geocode`/พิกัดไม่ตรงทะเบียน ให้บันทึกเป็น mapping issue และไม่แสดงผลเป็นของพื้นที่ที่ผิด

### 4.2 Endpoint ใหม่

เสนอ `GET /api/v1/forecast/hourly?area_code=<รหัส>&hours=24` โดย `hours` จำกัด 24 หรือ 48 ในระยะแรก รหัสพื้นที่ระบุระดับจากทะเบียน ไม่รับ query ชื่ออิสระเพื่อกัน cache แตกและการเรียก API โดยไม่จำกัด

ตัวอย่าง response เชิงสัญญา (ไม่ใช่รูปแบบ TMD ตรง ๆ):

```json
{
  "data": {
    "area": {"code": "730608", "level": "subdistrict", "province": "นครปฐม", "district": "สามพราน", "subdistrict": "ไร่ขิง"},
    "reference_point": {"lat": 13.742069, "lon": 100.272838},
    "hours": [{"time": "2026-09-27T20:00:00+07:00", "rain_mm": 0}],
    "summary": {"hours_returned": 24, "total_rain_mm": 0, "peak_rain_mm": 0},
    "source_status": "live"
  },
  "meta": {"source": "tmd", "status": "live", "fetched_at": "<ISO-8601>", "ttl_seconds": 3600}
}
```

- `time` คือเวลาที่พยากรณ์มีผล ไม่ใช่เวลาที่ดึงข้อมูล; เก็บ timezone `+07:00` จากต้นทาง ตรวจลำดับและชั่วโมงที่ขาด
- `total_rain_mm` รวมเฉพาะชั่วโมงที่คืนจริง; ถ้าขาดต้องแสดงจำนวนชั่วโมงและสถานะ `partial` ห้ามเติมศูนย์เอง
- เวลาที่แบบจำลองออกรุ่น (`model_run_at`) แสดงเฉพาะเมื่อ TMD ส่งค่าที่ตรวจสอบได้; ถ้าไม่มี ให้แสดงเพียง `fetched_at` และช่วงเวลาพยากรณ์
- `found: false`/ชื่อไม่ตรง, `not_configured`, `stale`, `partial`, `rate_limited` และโควตาไม่พอ ต้องแยกจากฝน `0 มม.`
- คง key ฝั่ง server ใน `.env` ไม่ส่งให้ browser ไม่ใส่ token ใน URL, error, log หรือไฟล์แผน

### 4.3 Cache และงบโควตา

- ใช้ cache key จากรหัสพื้นที่และจำนวนชั่วโมงที่ขอ; รวมคำขอพร้อมกันของพื้นที่เดียวกันด้วย lock ที่มีอยู่
- ก่อนใช้ผล cache ตรวจว่าช่วงอนาคตยังครบตามที่ UI ระบุ; TTL 3 ชั่วโมงของสรุปตำบลปัจจุบันอาจทำให้ผลที่เคยมี 24 ชั่วโมงเหลืออนาคตไม่ถึง 24 ชั่วโมง
- ทางเลือกแรก: เก็บ horizon สำรองและตัดชั่วโมงอดีตตอนส่งผล แต่คิดต้นทุน datapoints เพิ่ม; หรือ refresh เมื่อชั่วโมงอนาคตไม่พอ ตั้งเกณฑ์จากการวัดการใช้จริง ไม่ใช้ TTL อย่างเดียว
- คำขอ `24 h × rain` ใช้ 24 datapoints; `24 h × rain,cond` ใช้ 48 โดยประมาณ หากดึงมากกว่า 4,166 พื้นที่ × 24 ชั่วโมง × `rain` จะเกิน 100,000 datapoints ต่อหนึ่งรอบโควตาที่มี limit นี้ แม้ไม่รวมการใช้งาน TMD เดิม
- จำกัด concurrent upstream calls และมี rate limiter ต่ำกว่าเพดาน 60 requests/minute ที่ตรวจพบในระบบเดิม; สำรองโควตาให้พยากรณ์รายจังหวัดและคำขอพื้นที่เสี่ยง ไม่ทำการ refresh ทุกพื้นที่ตาม timer
- `cache_max_entries=512` ปัจจุบันไม่พอหากมีพื้นที่นิยมจำนวนมากหรือหลาย instance; ประเมิน persistent/shared cache เมื่อข้อมูลการใช้งานจริงถึงเกณฑ์ที่กำหนด
- เมื่อ TMD ส่ง 429 หรือ remaining ต่ำกว่า budget ที่ตั้งไว้ ให้คืน cache พร้อมป้าย `stale` หากมี; หากไม่มี ให้แจ้ง “ยังไม่มีพยากรณ์” ไม่แสดงศูนย์

## 5. แผนหน้าจอ

1. เพิ่มตัวเลือกแบบลำดับ จังหวัด → อำเภอ → ตำบล ในแผงพยากรณ์ แต่ละขั้นใช้ได้โดยไม่ต้องเลือกขั้นถัดไป เลือกจังหวัดแล้วแสดงฝนรายชั่วโมงของจุดอ้างอิงจังหวัด
2. แสดงกราฟแท่ง 24 ชั่วโมงเริ่มจากชั่วโมงปัจจุบันตามเวลาไทย พร้อมค่ารายชั่วโมงเมื่อแตะ/โฟกัส, ยอดสะสมช่วงที่แสดง, จุดอ้างอิง และเวลาอัปเดต
3. ติดป้าย “TMD · พยากรณ์ ณ จุดอ้างอิง” ให้ต่างจากชั้น “ฝนสะสม 24 ชม. (ThaiWater)” และกราฟ Open-Meteo ของพิกัดที่คลิก
4. มีสถานะ loading, ไม่พบพื้นที่, ชั่วโมงไม่ครบ, ข้อมูลเก่า, โควตาหมด และ API ขัดข้อง; ค่าฝนศูนย์แสดงเฉพาะเมื่อ TMD คืน `0`
5. เมื่อเปลี่ยนพื้นที่เร็ว ให้ยกเลิกหรือเพิกเฉยผลคำขอเก่า เพื่อไม่ให้กราฟของพื้นที่ก่อนหน้าทับพื้นที่ใหม่; รองรับมือถือและคีย์บอร์ด

## 6. ลำดับลงมือทำและเกณฑ์ผ่าน

### Phase 0 — ยืนยันทะเบียนพื้นที่และความครอบคลุม

- คัดเลือกทะเบียนพื้นที่ ตรวจสิทธิ์ใช้, รหัส, จำนวนพื้นที่, ชื่อซ้ำ และ mapping กับ TMD ตัวอย่างทุกภูมิภาค รวมกรุงเทพฯ เขต/แขวง
- ตรวจ TMD response schema, `geocode`, พิกัด, 24/48 ชั่วโมง, เวลาไทย, กรณีไม่พบ และ header โควตา ด้วยตัวอย่างที่มีฝนและไม่มีฝน

**ผ่านเมื่อ:** เลือกพื้นที่ตัวอย่าง 3 ระดับได้ถูกต้อง; มีรายงานพื้นที่ที่ TMD หาไม่พบและแนวทางแสดงผล

### Phase 1 — Backend และการคุมโควตา

- เพิ่มตัวอ่านทะเบียนพื้นที่และ service รายชั่วโมงบน `tmd.py`; ทำ response normalization โดยไม่แก้ความหมายของ `rain`
- เพิ่ม endpoint ใหม่ใน `routes.py`; ใช้รูปแบบ `meta`/ETag/stale fallback เดิม แต่เพิ่มการตรวจความครบของช่วงเวลา
- เพิ่ม quota guard, rate limiter, metrics ของ request, datapoints, cache hit/miss, 429 และพื้นที่ไม่พบ; ทดสอบการคืนผลเมื่อ upstream ล่ม

**ผ่านเมื่อ:** คำขอหนึ่งพื้นที่ไม่เกินงบที่คาด; invalid code ไม่เรียก TMD; cache ซ้ำไม่หักโควตา; 429 ไม่ทำให้ UI แสดงฝนศูนย์

### Phase 2 — UI และ rollout จำกัดวง

- เพิ่มตัวเลือกพื้นที่และกราฟใน `frontend/index.html`, `frontend/app.js`, `frontend/styles.css`; คง UI พยากรณ์รายวันและรายการตำบลน้ำท่วมเดิม
- ทดลองเปิดกับพื้นที่ตัวอย่างก่อน; วัดการใช้โควตาและความผิดพลาดของชื่อพื้นที่ แล้วจึงเปิดทุกพื้นที่ที่ mapping ผ่าน

**ผ่านเมื่อ:** เลือกจังหวัด/อำเภอ/ตำบลแล้วชื่อ พิกัด ชั่วโมง และค่าฝนตรง API; UI แยกพยากรณ์กับฝนวัดจริงชัดเจน

### Phase 3 — ขยายการใช้งานเมื่อจำเป็น

- หากต้องการภาพรวมหลายตำบลพร้อมกัน คำนวณงบโควตาจากจำนวนพื้นที่จริงและความถี่ refresh ก่อน อาจดึงเฉพาะพื้นที่น้ำท่วม/พื้นที่เฝ้าระวัง
- ทดสอบ `forecast/area/place` หรือ `forecast/area/watershed` เฉพาะกรณีที่ต้องใช้ grid/ลุ่มน้ำ พร้อมวัด datapoints และความหมายเชิงพื้นที่จริง ไม่ถือว่าเป็น API แบบ bulk ที่ถูกกว่าโดยอัตโนมัติ
- พิจารณา shared cache และงาน prefetch ที่มี budget/priority หากการใช้งานจริงทำให้ in-process cache ไม่พอ

**ผ่านเมื่อ:** พื้นที่ที่เปิดใช้งานไม่ทำให้โควตาหมดก่อนรอบรีเซ็ตที่ตรวจสอบแล้ว และไม่กระทบข้อมูล TMD เดิม

| กรณี | ผลที่ต้องได้ |
|---|---|
| จังหวัด, อำเภอ, ตำบลที่พบ | ส่ง query TMD ถูกระดับ; พิกัด/รหัสตรง; คืนชั่วโมงและยอดรวมถูก |
| ชื่อซ้ำต่างจังหวัดหรือพื้นที่เปลี่ยนชื่อ | ใช้ parent code และ mapping; ไม่แสดงข้อมูลพื้นที่ผิด |
| ชั่วโมงขาด, `rain=null`, เวลาไม่ต่อเนื่อง | แสดง `partial`; ไม่แทนค่าหายด้วย 0 |
| TMD คืนฝน 0 ทุกชั่วโมง | แสดง 0 มม. และสถานะข้อมูลปกติ |
| cache เก่าจนอนาคตไม่ครบ 24 ชั่วโมง | refresh หรือระบุช่วงจริง ไม่ติดป้าย “24 ชั่วโมงข้างหน้า” ผิด |
| token ไม่ตั้งค่า, 401, 429, quota ต่ำ, timeout | สถานะชัดเจน; ไม่รั่ว token; stale fallback เมื่อมีข้อมูลเดิม |
| ผู้ใช้เปลี่ยนพื้นที่เร็วและหลายคนเลือกพื้นที่เดียวกัน | ผลใหม่ไม่ถูกผลเก่าทับ; upstream call ซ้ำถูก coalesce |
| กรุงเทพฯ เขต/แขวง และชื่อมีคำนำหน้า | mapping ถูกต้องหรือแสดงไม่พบอย่างตรงไปตรงมา |

## 8. ไฟล์ที่คาดว่าจะเกี่ยวข้องเมื่ออนุมัติให้พัฒนา

- `backend/app/data/`: ทะเบียนพื้นที่และบันทึกที่มา/สิทธิ์ใช้
- `backend/app/services/tmd.py`, `backend/app/config.py`, `backend/app/services/cache.py`: ดึงข้อมูล รายชั่วโมง cache และโควตา
- `backend/app/api/routes.py`: endpoint ใหม่และสถานะข้อมูล
- `frontend/index.html`, `frontend/app.js`, `frontend/styles.css`: ตัวเลือกพื้นที่และกราฟ
- `tests/test_tmd.py` และ API/UI tests เพิ่มเติม; `README.md` อธิบายความหมายข้อมูลและข้อจำกัด

## 9. ข้อสรุปการตัดสินใจ

เริ่มจาก **on-demand 24 ชั่วโมงเมื่อผู้ใช้เลือกพื้นที่** ด้วย `fields=rain` และแสดงเป็นค่าที่จุดอ้างอิงของ TMD. ไม่ดึงทุกตำบลล่วงหน้า. คง API เดิม. วัดโควตาและ coverage ก่อนขยายเป็น 48 ชั่วโมงหรือหลายพื้นที่พร้อมกัน.
