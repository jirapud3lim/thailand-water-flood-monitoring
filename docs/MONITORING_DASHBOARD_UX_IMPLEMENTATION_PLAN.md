# แผนปรับปรุง UX/UI ของ Monitoring Dashboard

วันที่จัดทำ: 27 กันยายน 2026  
สถานะ: แผนเท่านั้น ยังไม่แก้โค้ด

## 1. เป้าหมาย

ทำให้ผู้ใช้ตอบคำถามหลักได้เร็วขึ้น: **พื้นที่ไหนควรดู**, **ตัวเลขและหมุดนับอะไร**, และ **จะดูข้อมูลฝนหรือชั้นข้อมูลของพื้นที่นั้นอย่างไร** โดยรักษาความสามารถสำหรับผู้ใช้ที่ต้องสำรวจข้อมูลเชิงลึก

แผนนี้อิงหน้าเว็บที่รันจริงบนเดสก์ท็อปขนาด 1280 × 720 พิกเซล และโค้ดปัจจุบันใน `frontend/index.html`, `frontend/styles.css`, `frontend/app.js` ยังไม่ได้ทดสอบภาพจริงบนมือถือหรือกับผู้ใช้ จึงให้ทดสอบก่อนยืนยันว่าการจัดวางใหม่ดีขึ้น

### สิ่งที่ดีอยู่แล้วและต้องรักษา

- ภาพรวม รายการจุดเตือน และแผนที่อยู่ในลำดับที่สแกนสถานการณ์ได้เร็ว
- รายการแสดงจุดเด่นเพียงบางส่วน พร้อมชื่อพื้นที่ เวลา และระดับเตือน
- หมุดใช้ชนิดสัญลักษณ์ รูปทรง สี และข้อความร่วมกัน ไม่ควรย้อนกลับไปพึ่งสีอย่างเดียว
- ข้อมูล TMD แยกพยากรณ์จากฝนตรวจวัดจริง และดึงรายชั่วโมงเมื่อผู้ใช้กดดูเท่านั้นเพื่อคุมโควตา
- โหมดแสดงเฉพาะจุดเสี่ยงและกฎตามระดับซูมช่วยลดจุดบนแผนที่อยู่แล้ว

## 2. ขอบเขตและข้อห้าม

ปรับข้อความ ลำดับและการเข้าถึงส่วนต่าง ๆ การสื่อสารขอบเขตข้อมูล สถานะบนมือถือ และการลดการทับกันของแผนที่ ไม่เปลี่ยนเกณฑ์ความรุนแรง สูตรคำนวณน้ำในเขื่อน แหล่งข้อมูล หรือสัญญา API โดยไม่มีเหตุผลจากการทดสอบ

ห้ามทำให้จำนวนจุดบนแผนที่ดูเท่าจำนวนจุดเตือนด้วยการซ่อนความต่างของนิยาม ห้ามตีความ “ไม่มีหมุด” ว่า “ปลอดภัย” และห้ามเรียก TMD อัตโนมัติเมื่อเลือกจังหวัดหรือเปิดแผง

## 4. ลำดับดำเนินงาน

### Phase 0 — เก็บฐานและยืนยันนิยาม

1. บันทึกภาพและเส้นทางงานบนเดสก์ท็อป 1280 × 720 และมือถืออย่างน้อย 390 × 844 พิกเซล โดยทดสอบทั้งข้อมูลครบ ข้อมูลสำรอง และแหล่งข้อมูลล้มเหลว
2. วัดเวลาหรือจำนวนขั้นตอนของงาน 4 งาน: เลือกจังหวัดเสี่ยง, เปิดสถานีวิกฤต, ดูพยากรณ์ฝนรายตำบล, และปิด/เปิดชั้นข้อมูล
3. ระบุนิยามของจำนวนทุกจุดในหน้า ได้แก่ แหล่งข้อมูล การนับสถานีคู่ ขอบเขตจังหวัดหรือจอ กฎระดับซูม โหมดจุดเสี่ยง และการซ่อนเมื่อปิดชั้นข้อมูล
4. ใช้ข้อมูลจำลองคงที่ในการทดสอบ UI เพื่อไม่ให้ตัวเลขและเวลาเปลี่ยนระหว่างเปรียบเทียบ ก่อนและหลังปรับ

**เกณฑ์ผ่าน:** ทีมอธิบายได้ว่า KPI แต่ละตัวต่างจากจำนวนหมุดอย่างไร และมีภาพ/ผลวัดฐานก่อนแก้

### Phase 1 — ทำความหมายของจำนวนและขอบเขตให้ชัด (P1)

1. เปลี่ยนคำกำกับ KPI เป็นข้อความที่บอกขอบเขตและการนับไม่ซ้ำ เช่น “จุดถึงระดับเตือนในจอ (นับไม่ซ้ำ)” หรือ “ใน จ.…” โดยใช้คำสั้นที่พอดีกับพื้นที่จริง และอธิบายประเภทจุดใกล้ KPI
2. แยกจำนวนที่หัวข้อชั้นข้อมูลเป็น “หมุด ปภ. ที่แสดง” และ “หมุด ปภ. ที่ซ่อน” อย่าใช้คำว่า “จุดเตือน” กับจำนวนหมุดหลังกรอง
3. แยกเหตุที่ซ่อนอย่างถูกต้อง: ระดับซูม, โหมดเฉพาะจุดเสี่ยง, และการปิดชั้นข้อมูล หากแสดงผลรวม ให้ผลรวมเท่ากับจำนวนที่โหลดในขอบเขตเดียวกัน; อย่านำเหตุจากคนละฐานมารวมในวงเล็บเดียว
4. เพิ่มคำอธิบายสั้นใกล้จำนวน หรือปุ่ม “นับอย่างไร” ที่เปิดรายละเอียดได้โดยไม่ต้องเลื่อนไปท้าย sidebar
5. คงเวลาข้อมูลและสถานะสำรองไว้ใกล้ KPI; ทดสอบสถานะไม่มีข้อมูลและโหลดล้มเหลวโดยไม่แสดง `0` ที่สื่อว่าปลอดภัย

**จุดแก้ที่คาด:** `renderPriority()`, `updateLayerCounts()`, `renderFloodPoints()`, `renderThaiWater()`, ส่วน KPI และหัวข้อชั้นข้อมูลใน `frontend/index.html`

**เกณฑ์ผ่าน:** ผู้ทดสอบที่ไม่เห็นโค้ดอธิบายความต่างระหว่าง KPI และจำนวนหมุดได้อย่างน้อย 4 ใน 5 คน; จำนวนแสดงตรงกับกฎกรองในทุกกรณีทดสอบ

### Phase 2 — ลดระยะค้นหาและเชื่อมบริบทจังหวัด (P1)

1. คงภาพรวมและรายการจุดเตือนไว้บนสุด เพิ่มทางลัดที่มองเห็นได้ไปยัง “พยากรณ์ฝน”, “ชั้นข้อมูล” และ “คำอธิบายสัญลักษณ์” บนเดสก์ท็อปและมือถือ
2. จัดตัวเลือกชั้นข้อมูลขั้นสูงเป็นกลุ่มพับได้ แต่คงสถานะเปิด/ปิดของชั้นที่สำคัญให้เห็นชัด ห้ามซ่อนคำเตือนเรื่องข้อมูลที่อาจเก่า
3. ใช้จังหวัดจาก “จุดที่ควรดู” เพื่อเติมจังหวัดในฟอร์มพยากรณ์เมื่อผู้ใช้กดทางลัด “ดูฝนจังหวัดนี้” เท่านั้น ไม่ดึงพยากรณ์จนกด “ดูพยากรณ์”
4. ระบุหัวข้อแยกให้ชัดว่า “ขอบเขตรายการจุดเตือน” กับ “พื้นที่พยากรณ์ฝน” เพราะการเลือกระดับอำเภอ/ตำบลไม่มีผลต่อจำนวนจุดเตือนหรือขอบเขตแผนที่
5. เมื่อเปลี่ยนจังหวัดในฟอร์มพยากรณ์ ล้างอำเภอ/ตำบลและผลเดิมทันที; หากจังหวัดในสองส่วนต่างกัน ให้แสดงชื่อจังหวัดของผลพยากรณ์ทุกครั้ง ไม่อ้างว่าเป็นพื้นที่เดียวกับแผนที่
6. รองรับการกลับมาจากรายละเอียดจุดบนมือถือโดยไม่สูญเสียตำแหน่งเลื่อนและตัวเลือกเดิม

**จุดแก้ที่คาด:** โครง `aside` และทางลัดใน `frontend/index.html`; `setScope()`, ตัวเลือกพื้นที่ TMD และ `setSidebarOpen()` ใน `frontend/app.js`; layout ใน `frontend/styles.css`

**เกณฑ์ผ่าน:** จากหน้าแรก ผู้ใช้เข้าถึงพยากรณ์และชั้นข้อมูลได้ในไม่เกิน 2 การกระทำ; การเลือกจังหวัดในรายการไม่ใช้โควตา TMD; ไม่แสดงผลพยากรณ์ของจังหวัดเดิมหลังเปลี่ยนพื้นที่

### Phase 3 — ลดการทับกันของแผนที่ (P2)

1. ตรวจภาพที่ระดับประเทศ จังหวัด และสถานีทั้งสองขนาดจอ โดยเปิด/ปิดเรดาร์และดาวเทียม รวมถึงโหมดเฉพาะจุดเสี่ยง
2. ทดลองรวมหมุดที่ใกล้กันเมื่อซูมไกล โดยกลุ่มต้องแสดงระดับสูงสุดและจำนวนจุดวิกฤต; กดแล้วซูมหรือเปิดรายการได้ ห้ามปล่อยให้กลุ่มสีทั่วไปบังจุดวิกฤต
3. ทดลองลดขนาดแผงเขื่อนเป็นสรุปเมื่อเปิดแผนที่ครั้งแรก โดยคงทางเปิดรายการเดิมและสถานะผู้ใช้หลังย่อ/ขยาย
4. ตรวจลำดับชั้นของเรดาร์ ดาวเทียม หมุด และ popup เพื่อไม่ให้ชั้นทึบหรือแผงลอยบังจุดที่เลือก
5. ประเมินประสิทธิภาพเมื่อมีสถานีจำนวนมากก่อนเลือกวิธีรวมหมุด; เก็บกฎซูมเดิมเป็นทางถอยหากวิธีใหม่ช้าหรือทำจุดสำคัญหาย

**จุดแก้ที่คาด:** การวาดหมุดและแผงเขื่อนใน `frontend/app.js`; `.map-dam-panel` และสไตล์หมุดใน `frontend/styles.css`

**เกณฑ์ผ่าน:** จุดวิกฤตทุกจุดยังเข้าถึง popup ได้; ไม่มีแผงลอยบังปุ่มหลักบนมือถือ; การเลื่อน/ซูมไม่สะดุดกว่า baseline ที่วัดใน Phase 0

### Phase 4 — อ่านง่ายและตรวจการเข้าถึง (P2)

1. กำหนดขนาดขั้นต่ำเชิงออกแบบของข้อความรองที่สำคัญ โดยเริ่มตรวจรายการจุดเตือน สถานะข้อมูล คำอธิบาย จำนวนชั้น และเวลา; ทดสอบภาษาไทยที่ 100% และ 200% zoom
2. แสดงข้อความสถานะระบบสั้น ๆ บนมือถือ เช่น “ครบ 6 แหล่ง” หรือ “ขาด 1 แหล่ง” แทนจุดสีอย่างเดียว; ให้รายละเอียดต่อแหล่งเปิดอ่านได้
3. ตรวจขนาดพื้นที่กดของสวิตช์ ทางลัด แผงเขื่อน และรายการจุดเตือนที่หน้าจอแคบ
4. ตรวจการใช้งานด้วยแป้นพิมพ์และเครื่องอ่านหน้าจอ: ชื่อปุ่ม, สถานะพับ/ขยาย, focus หลังเปิด/ปิด sidebar, และการประกาศผลพยากรณ์หรือข้อผิดพลาด
5. ตรวจความต่างระหว่างสถานะ “โหลดอยู่”, “ไม่มีข้อมูล”, “ข้อมูลเก่า”, “แหล่งล้มเหลว” และ “ไม่มีจุดเตือน” ด้วยข้อความและสัญลักษณ์ ไม่ใช้สีเพียงอย่างเดียว

**จุดแก้ที่คาด:** `frontend/styles.css`, `frontend/index.html`, `renderHealth()`, `setSidebarOpen()` และส่วนแสดงผลพยากรณ์ใน `frontend/app.js`

**เกณฑ์ผ่าน:** ผู้ทดสอบอ่านสถานะระบบบนมือถือได้โดยไม่ต้องเปิดเมนู; ไม่มีข้อความสำคัญถูกตัดที่ 390 × 844 และ 200% zoom; ทุกทางลัดใช้แป้นพิมพ์ได้

## 5. การทดสอบและส่งมอบ

- เพิ่ม automated tests ของนิยามจำนวน กฎซ่อนหมุด การเปลี่ยนขอบเขต และการล้างผลพยากรณ์เมื่อเปลี่ยนพื้นที่
- ทดสอบ UI กับข้อมูลจำลองครบ/สำรอง/ล้มเหลว และขนาดจอ 390 × 844, 820 × 900, 1280 × 720 และ 1440 × 900 พิกเซล
- ทดสอบมืออย่างน้อย 5 คนที่ไม่พัฒนาโปรเจกต์ โดยให้ทำ 4 งานจาก Phase 0; บันทึกความสำเร็จ เวลา จุดที่เข้าใจผิด และคำอธิบายตัวเลขของแต่ละคน
- เปรียบเทียบผลกับ baseline ก่อนแก้ ไม่ใช้ความรู้สึกว่าหน้า “โล่งขึ้น” เป็นเกณฑ์เดียว
- แยกส่งงานตาม Phase เพื่อย้อนกลับได้ ตรวจ regression ของแผนที่ รายการจุดเตือน และ TMD quota หลังแต่ละ Phase

## 6. ลำดับที่แนะนำ

เริ่ม Phase 0 ก่อน แล้วทำ Phase 1 และ Phase 2 เพราะแก้ความหมายกับเส้นทางงานหลัก Phase 3 และ Phase 4 ทำต่อหลังมีผลทดสอบจริง หากภาพมือถือชี้ว่าข้อความสถานะอ่านไม่ได้ ให้ย้ายส่วนสถานะของ Phase 4 ขึ้นมาทำพร้อม Phase 1

แผนนี้ไม่รวมการเปลี่ยนคะแนนความเสี่ยงของเขื่อนหรือการไฮไลท์ลำน้ำท้ายเขื่อน ซึ่งเป็นงานคนละขอบเขต

## 7. สถานะการดำเนินการ (27 กันยายน 2026)

### 7.3 สิ่งที่เปลี่ยน

- **Phase 1 ตัวเลข:**
  - KPI บอกขอบเขตและ "นับไม่ซ้ำ" มีเวลาและสถานะข้อมูลอยู่ใต้ตัวเลข
  - มี "ตัวเลขนี้นับอย่างไร" ติดกับ KPI
  - โหลดล้มเหลวแสดง "—" และข้อความว่าไม่ทราบ ไม่แสดง 0
  - เมื่อไม่พบจุดเตือน บอกว่า "ไม่ยืนยันว่าปลอดภัย"
- **Phase 2 เส้นทางงาน:**
  - แถบทางลัดติดบนสุดของ sidebar
  - กลุ่ม ThaiWater และคำอธิบายสัญลักษณ์พับได้ จำสถานะการพับไว้ หัวกลุ่มยังบอกจำนวนชั้นที่เปิดและชั้นที่ล้มเหลวหรือใช้ข้อมูลสำรอง
  - ปุ่ม "ดูพยากรณ์ฝนรายชั่วโมง จ.…" เติมจังหวัดลงฟอร์มโดยไม่เรียก TMD
  - ผลพยากรณ์ที่เป็นคนละจังหวัดกับรายการจุดเตือนมีป้ายบอก
  - บนมือถือ ปิดเมนูแล้วเปิดใหม่ ตำแหน่งเลื่อนและ focus กลับมาที่รายการเดิม และรายการไม่ถูกโหลดใหม่ระหว่างบินไปยังสถานี
- **Phase 3 แผนที่:**
  - หมุด ปภ. ที่ห่างกันไม่เกิน 30 px รวมเป็นกลุ่มเมื่อซูมต่ำกว่า 12 กลุ่มใช้สีและสัญลักษณ์ของจุดที่รุนแรงที่สุด กดแล้วเห็นรายการสมาชิก
  - สถานีที่กำลังโฟกัสหรือเปิด popup อยู่ไม่ถูกรวมกลุ่ม
  - ปิดการรวมกลุ่มได้ด้วย `state.clusterEnabled = false` เวลาวาดวัดได้ 0.5 ms (รวมกลุ่ม) เทียบกับ 1.1 ms (หมุดเดี่ยว)
  - แผงเขื่อนย่อเป็นค่าเริ่มต้น และเลื่อนแผนที่หลบเมื่อ popup เปิดใต้แผง
- **Phase 4 อ่านง่าย:**
  - ขยายตัวอักษรรอง
  - สถานะบนหัวเว็บเป็นปุ่มที่มีข้อความสั้น พร้อมรายการรายแหล่ง
  - พื้นที่กดขั้นต่ำ 30 px
  - Escape ปิดเมนูและรายการสถานะ แล้ว focus กลับไปที่ปุ่ม
  - `aria-busy` และ `aria-live` ที่รายการและ KPI
  - สถานะโหลด ล้มเหลว และไม่มีจุดเตือน ใช้ทั้งข้อความและสัญลักษณ์

## 9. ปรับเป็นรูปแบบ modern (27 กันยายน 2026)

แนวทางคือแผนที่เต็มจอกับแผงลอย ตามแบบแดชบอร์ดแผนที่ปัจจุบัน เช่น Google Flood Hub และบน Google Maps มือถือใช้ bottom sheet (NN/g, Material 3) ไม่เปลี่ยน id หรือโครง DOM ที่ JavaScript และเทสต์ใช้อยู่ งานส่วนใหญ่เป็น CSS ที่ต่อท้าย `frontend/styles.css`

- **Design token ชุดเดียว:**
  - ฟอนต์ Inter กับ Noto Sans Thai จาก Google Fonts มี system font เป็นตัวสำรอง
  - รัศมีมุม 9 / 12 / 18 px
  - พื้นผิวกระจก (`backdrop-filter`) เงาเดียวกันทุกแผง
  - ตัวเลขใช้ความกว้างเท่ากัน (tabular)
- **เดสก์ท็อป:**
  - แผนที่เต็มจอ แผงควบคุมกว้าง 360 px ลอยทางซ้าย
  - ปุ่มซูม, ป้ายเวลาเรดาร์ และตัวเลือกแผนที่ขยับไปอยู่ถัดจากแผง
  - มุมมองเริ่มต้น, ปุ่มกลับบ้าน, fit จังหวัด และ autoPan ของ popup เว้นระยะให้แผง (`panelInset`, `offsetCenter`)
- **มือถือ (≤ 820 px):**
  - แผงกลายเป็น bottom sheet ตอนย่อสูง `min(232px, 42vh)` แสดงเฉพาะ KPI และชิปแยกระดับ
  - กด KPI, แถบจับ หรือปุ่มเมนูเพื่อขยาย ขยายแล้วสูงประมาณ 86vh
  - ตัดปุ่มลอย "N จุดเตือน" ออก เพราะ sheet แสดงข้อมูลนี้อยู่แล้ว
  - ปุ่มบนแผนที่และ popup เว้นระยะเหนือ sheet
- **Footer:** ตัดแถบ footer ออก เครดิตแหล่งข้อมูลย้ายไปอยู่ในบรรทัด attribution ของแผนที่
- **Focus:** แก้ให้หลังจากรายการถูกโหลดใหม่ ระหว่างที่ผู้ใช้ดู popup ยังคืน focus ไปที่สถานีเดิมได้ (`data-key`)

ทดสอบ:

- pytest ผ่าน 147 รายการ
- node ผ่าน 10 รายการ
- บันทึก fixture ใหม่ เพราะมุมมองเริ่มต้นเปลี่ยน แล้วรันเช็กลิสต์ headless Chromium ผ่าน 56/56 สองรอบติดกัน

ยังไม่ได้ทำ:

- ยังไม่มีท่าลาก sheet ด้วยนิ้ว ตอนนี้ใช้การแตะ
- ยังไม่ได้ทดสอบบนเครื่องจริงที่ไม่รองรับ `backdrop-filter` ซึ่งจะเห็นเป็นพื้นทึบแทน

### 9.1 แก้ปุ่มทางลัดถูกตัด (27 กันยายน 2026)

**ปัญหา:** ปุ่มทางลัด 5 ปุ่มต้องใช้ความกว้าง 406 px แต่แผงมองเห็นได้ 358 px ปุ่ม "สัญลักษณ์" จึงถูกตัด แถบเลื่อนแนวนอนก็ถูกซ่อนไว้ ผู้ใช้จึงไม่รู้ว่ามีปุ่มซ่อนอยู่

**ที่แก้:**

## 10. เรดาร์ฝนแบบ Windy (27 กันยายน 2026)

**Backend:** `backend/app/services/radar_tiles.py` และ `GET /api/v1/radar/tiles/{frame}/{z}/{x}/{y}.png`

- **Cache:** เก็บ tile แบบ LRU จำกัดขนาด 96 MB หลายคนขอ tile เดียวกันพร้อมกันจะดึงต้นทางครั้งเดียว ตอบกลับด้วย `Cache-Control: immutable`
- **จำกัดการเรียกต้นทาง:** ไม่เกิน 90 ครั้ง/นาที ถ้าโควตาเต็มจะรอได้ไม่เกิน 8 วินาที เกินจากนั้นตอบ 503 พร้อม `Retry-After`
- **กันการใช้เป็น open proxy:** ให้เฉพาะเฟรมที่ RainViewer ยังแสดงอยู่ และ zoom ไม่เกิน 7
- **ขนาด tile:** ใช้ 512 px ซึ่งยังใช้ได้ในรุ่นฟรี (ทดสอบวันที่ 27 ก.ย. 2026) จำนวนคำขอลดลง 4 เท่า

**Frontend:**

- **ชั้นภาพ:** แต่ละเฟรมเป็น tile layer แยก โหลดล่วงหน้าเรียงจากเฟรมล่าสุด แล้วใช้ CSS cross-fade ระหว่างเฟรม
- **การเล่น:** เฟรมละ 0.6 วินาที ค้างที่เฟรมล่าสุด 1.6 วินาที ถ้าเฟรมถัดไปยังโหลดไม่เสร็จจะรอแทนการแสดงจอว่าง
- **แถบเวลาด้านล่างแผนที่:** ย้าย `#radar-range` และ `#radar-play` ออกจากแผงชั้นภาพมาไว้ที่นี่ แก้ `tests/test_dashboard_controls.py` ให้ตรวจว่าแต่ละตัวมีชิ้นเดียวและไม่อยู่ใน sidebar ตามเจตนาเดิมของเทสต์
- **ความคมชัด:** เลยจาก zoom 8 ไปจะเบลอนุ่ม
- **tile ที่ได้ 503:** ลองโหลดใหม่สูงสุด 3 ครั้ง

## 11. แผนที่ประเทศไทยอยู่กลางพื้นที่ที่มองเห็น (28 กันยายน 2026)

**สาเหตุ:** กรอบล็อก `setMaxBounds(THAILAND_BOUNDS)` ทำให้ Leaflet จัดกรอบประเทศไทยไว้กลาง container ทั้งหมด การเลื่อนจุดกึ่งกลาง (`offsetCenter`) ที่ใส่ไว้ชดเชยแผงลอยจึงไม่มีผล แต่แผงยังบังด้านซ้าย 412 px ประเทศไทยเลยดูชิดซ้าย บนมือถือเกิดแบบเดียวกันในแนวตั้ง เพราะ sheet บังด้านล่าง

**ที่แก้:**

- **เดสก์ท็อป:** container ของแผนที่เริ่มถัดจากแผง (`.map-shell { margin-left }`)
- **มือถือ:** container จบที่ขอบบนของ sheet ตอนย่อ (`margin-bottom: var(--peek)`)
- **ผล:** กึ่งกลาง container ตรงกับกึ่งกลางที่มองเห็น
- **โค้ดที่ลบ:** `offsetCenter`, `panelInset`, `sheetInset` และ padding ของ popup ที่เคยชดเชย
- **ตัวที่วางบนแผนที่:** แถบเวลา, ตัวเลือกแผนที่ และคำอธิบายสีภูมิประเทศ กลับไปใช้ระยะจากขอบแผนที่ตามปกติ

**ผลวัด:** ระยะคลาดจากกึ่งกลางของพื้นที่ที่มองเห็น

| จอ | คลาดแนวนอน | คลาดแนวตั้ง |
|---|---|---|
| 1440, 1280, 900 px | 0 px | 6–9 px |
| 390 px | 9 px | 9 px (เดิม 122 px) |

**ปุ่มกลับบ้าน:** ให้ผลเท่ากันทุกขนาดจอ

**ทดสอบ:** เพิ่มเช็ก 2 ข้อในเช็กลิสต์ ผ่าน 63/63 · pytest 156 · node 17

## 12. ทิศทางน้ำในแม่น้ำ (28 กันยายน 2026)

**หลักการ:** น้ำไหลจากที่สูงไปที่ต่ำ ในแม่น้ำเดียวกัน สถานีที่ระดับน้ำ ม.รทก. สูงกว่าคือต้นน้ำ

ตรวจกับข้อมูลจริงแล้ว เรียงได้ถูกลำดับทั้ง 3 แม่น้ำ:

- เจ้าพระยา: นครสวรรค์ → สมุทรปราการ
- ปิง: เชียงดาว → นครสวรรค์
- มูล: นครราชสีมา → อุบลราชธานี

**Backend:** `backend/app/services/river_flow.py` และ `GET /api/v1/river-flow`

- ใช้ข้อมูลระดับน้ำ ThaiWater จาก cache เดียวกับ `/thaiwater/water-level` จึงไม่เรียกต้นทางเพิ่ม
- จัดกลุ่มสถานีตาม (ลุ่มน้ำ, ชื่อแม่น้ำ)
- รวมสถานีที่อยู่ห่างกันไม่เกิน 1 กม. เป็นจุดเดียว
- ไม่เชื่อมสถานีที่ห่างกันเกิน 150 กม. เพราะอาจเป็นคนละสาขา
- ช่วงที่ปลายน้ำต่ำกว่า 2.5 ม.รทก. ถือเป็นช่วงน้ำทะเลหนุน และไม่ระบุว่าน้ำขึ้นหรือลง
- ใช้แนวโน้มของสถานีต้นน้ำเป็นแนวโน้มของช่วง: ขึ้นหรือลงตั้งแต่ 5 ซม.

**ข้อมูลทั้งประเทศ:** 316 ช่วงใน 97 แม่น้ำ

**Frontend:**

- **สวิตช์:** "ทิศทางน้ำในแม่น้ำ" ในกลุ่ม ThaiWater
- **เส้นเชื่อม:** เส้นตรงระหว่างสถานี มีลูกศรชี้ไปท้ายน้ำ
  - ส้ม = ต้นน้ำกำลังขึ้น
  - ฟ้า = ลด
  - ประเทา = ช่วงน้ำทะเลหนุน
  - ที่ zoom ต่ำกว่า 7 แสดงเฉพาะช่วงที่กำลังขึ้น
- **ชั้นแสดงผล:** วาดบน canvas ของตัวเองที่ไม่รับการคลิก อยู่ใต้สถานี
- **popup สถานี:** บอกสถานีต้นน้ำและท้ายน้ำ และเตือนเมื่อต้นน้ำกำลังขึ้น

**ข้อจำกัดที่แสดงบนหน้าจอ:**

- ไม่ใช่แนวลำน้ำจริง
- ไม่ได้บอกเวลาที่น้ำจะมาถึง
- ช่วงน้ำทะเลหนุนอาจไหลกลับ

**ข้อ 3 ที่เคยเสนอ (เทียบภาพน้ำท่วม GISTDA 1 วันกับ 7 วัน) — ไม่ได้ทำ:** ตรวจแล้วพบว่าชุดข้อมูลเป็นช่วงสะสมซ้อนกัน คือ 7 วันรวมข้อมูล 1 วันไว้แล้ว และดาวเทียมเรดาร์ไม่ได้ผ่านทุกพื้นที่ทุกวัน ถ้าบริเวณหนึ่งไม่พบน้ำในภาพ 1 วัน อาจแปลว่ายังไม่มีดาวเทียมผ่าน ไม่ได้แปลว่าน้ำลดแล้ว ถ้าแสดงผลเป็น "ทิศทางที่น้ำขยาย" จะชวนให้เข้าใจผิด ต้องใช้ข้อมูลรอบการถ่ายภาพของแต่ละช่องมาประกอบก่อน
