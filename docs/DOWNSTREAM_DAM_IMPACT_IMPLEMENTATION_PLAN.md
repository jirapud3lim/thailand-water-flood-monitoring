# แผนพัฒนา: ไฮไลท์ลำน้ำท้ายน้ำจากการระบายน้ำของเขื่อน

วันที่จัดทำ: 27 กันยายน 2026  
สถานะ: แผนงาน ยังไม่แก้โค้ดหรือเชื่อมข้อมูลใหม่

## 1. เป้าหมายและขอบเขต

เมื่อเลือกเขื่อนบนแผนที่ ให้เห็นลำน้ำและสถานีตรวจวัดที่อยู่ท้ายน้ำของเขื่อนนั้น พร้อมหลักฐานที่ใช้ประเมินสถานการณ์ เช่น ปริมาณระบายล่าสุด ระดับน้ำ และแนวโน้มสถานี ระบบต้องแยก **ความเชื่อมโยงทางน้ำ** ออกจาก **หลักฐานว่าระดับน้ำท้ายน้ำสูง** และ **ผลกระทบที่แบบจำลองยืนยัน**

ระยะแรกแสดงทางน้ำและสถานีที่ควรเฝ้าดู ไม่พยากรณ์เวลาน้ำถึง ไม่ระบุว่าพื้นที่ใดจะท่วม และไม่ออกประกาศเตือนภัยแทนหน่วยงานรัฐ

### คำศัพท์ใน UI

| คำ | ความหมาย | เงื่อนไขใช้ |
|---|---|---|
| ลำน้ำท้ายน้ำที่เกี่ยวข้อง | เส้นทางน้ำที่เชื่อมจากจุดระบายของเขื่อนตามโครงข่ายที่ตรวจสอบแล้ว | มีการยืนยัน topology และจุดปล่อยน้ำ |
| ควรติดตาม | เขื่อนระบายเพิ่ม หรือมีประกาศเกี่ยวกับการระบาย โดยยังไม่มีหลักฐานว่าระดับน้ำท้ายน้ำสูง | มีข้อมูลสดและเกณฑ์การเปลี่ยนแปลงที่ผ่านการทดสอบ |
| ระดับน้ำท้ายน้ำสูง | สถานีบนเส้นทางที่ยืนยันแล้วถึงเกณฑ์ของสถานีนั้น | มีค่าระดับน้ำและเวลาวัดที่ยังสด |
| คาดการณ์ผลกระทบ | ช่วงน้ำหรือพื้นที่ที่คำนวณจากแบบจำลองที่สอบเทียบแล้ว | ระยะหลังเท่านั้น |

คำว่า “เขื่อนวิกฤต” ไม่ใช่สถานะข้อมูลปัจจุบัน โค้ดจัด `percent_storage` เป็น `low`, `normal`, `high`, `very_high`; มากกว่า 100% คือ “สูงมาก (เกินความจุระดับเก็บกัก)” ตามเกณฑ์แสดงผลของโครงการ ไม่ใช่การยืนยันว่าจะมีน้ำท่วมท้ายน้ำ

## 2. สิ่งที่มีแล้วและช่องว่าง

| ข้อมูล | มีแล้ว | ช่องว่างต่อการไฮไลท์ท้ายน้ำ |
|---|---|---|
| เขื่อน RID + พิกัด DPM | `/api/v1/dams` มีพิกัด, ความจุ, `% กักเก็บ`, `inflow`, `outflow`, วันที่ข้อมูล; cache ตั้งต้น 3,600 วินาที | ไม่มีตำแหน่งทางระบายจริง, ลำน้ำปลายทาง, เวลา/รูปแบบการระบายรายชั่วโมง, ประกาศแผนระบาย และเกณฑ์ปลอดภัยท้ายน้ำ |
| สถานี ThaiWater / DPM | ระดับน้ำ พิกัด ชื่อแม่น้ำ/ลุ่มน้ำ ความรุนแรงตามเกณฑ์สถานี และเวลาวัด | ไม่มีรหัสช่วงลำน้ำหรือทิศทางการไหลสำหรับผูกสถานีกับเขื่อนโดยตรง |
| คลองและประตูน้ำ ThaiWater | พิกัด ระดับน้ำหน้า/ท้ายประตู บางสถานีมีระดับเตือน | ไม่มีกราฟทางน้ำ/คลองและสถานะการเดินเครื่องที่เชื่อถือได้สำหรับอนุมานทางไหล |
| Open-Meteo Flood | discharge แบบจำลองรายวัน ณ พิกัดที่คลิก | ไม่ได้เชื่อมกับการสั่งระบายเฉพาะเขื่อน จึงใช้ยืนยันผลกระทบจากเขื่อนไม่ได้ |
| GIS | มีแผนที่พื้นหลังและ GeoJSON จุด | ไม่มีเส้นลำน้ำและ topology ท้ายน้ำที่ผ่านการตรวจสอบ |

## 3. หลักการประเมิน

1. **ความเชื่อมโยง:** เขื่อนระบายลงช่วงลำน้ำใด แล้วไหลผ่านช่วงใดต่อไป ต้องตรวจสอบทิศทางและจุดเชื่อม ไม่จับคู่ด้วยชื่อหรือระยะทางอย่างเดียว
2. **สัญญาณการระบาย:** ใช้ปริมาณระบายและเวลาอ้างอิง เปรียบกับค่าก่อนหน้า/ค่าปกติของเขื่อนนั้น หากข้อมูลมีเพียงยอดรายวัน ให้แสดงเป็นบริบท ไม่คำนวณเวลาเดินทางของน้ำ
3. **สภาพท้ายน้ำ:** ใช้ระดับน้ำเทียบเกณฑ์สถานี แนวโน้ม ฝนในพื้นที่ และการระบายของเขื่อนอื่นที่เชื่อมกัน เพื่อให้เห็นภาพร่วม
4. **ระดับหลักฐาน:** สีของเส้นทางไม่เปลี่ยนเป็นระดับภัยเพียงเพราะ `% กักเก็บ` สูง การยกระดับต้องมีหลักฐานจากสถานี/ประกาศ หรือแบบจำลองที่ตรวจสอบแล้ว
5. **ไม่สรุปเหตุและผลเกินข้อมูล:** สถานีท้ายน้ำสูงพร้อมกับเขื่อนระบายมาก แสดงว่าเป็นเหตุการณ์ที่ต้องตรวจสอบร่วมกัน ไม่พิสูจน์ว่าการระบายเป็นสาเหตุเดียว

## 4. ข้อมูลที่ต้องจัดหาและตรวจสิทธิ์

### 4.1 โครงข่ายลำน้ำ

- สำรวจข้อมูลเส้นแม่น้ำและลำคลองของหน่วยงานไทยเป็นตัวเลือกแรก ตรวจความละเอียด ทิศทางการไหล สิทธิ์ใช้ และรหัสช่วงลำน้ำ
- หากไม่มีข้อมูลครบ ใช้ HydroRIVERS เป็นโครงข่ายตั้งต้นสำหรับแม่น้ำหลัก ข้อมูลมีรหัสช่วงและ `NEXT_DOWN` สำหรับเดินตามลำน้ำ แต่ต้องตรวจจุดต่อและลำน้ำไทยที่ขาดก่อนเผยแพร่
- จัดเก็บเป็นกราฟมีทิศทาง: `reach_id`, geometry, `downstream_reach_id`, basin, ชื่อแสดงผล, source, version
- ไม่สมมติว่าคลองชลประทาน คลองเมือง ทางผันน้ำ และบริเวณน้ำขึ้นลงเป็นทางไหลทิศเดียว กำหนด edge ชนิด `regulated` หรือ `unknown` และหยุดการไฮไลท์อัตโนมัติที่จุดไม่แน่ใจ

### 4.2 ตารางจับคู่เขื่อนและสถานี

- เขื่อนแต่ละแห่งต้องมีรหัส RID ที่คงที่, จุดปล่อยน้ำ, `release_reach_id`, เจ้าของข้อมูล, วันที่ตรวจสอบ และสถานะ `verified`/`pending`/`unsupported`
- สถานีแต่ละแห่งต้องมี `station_id`, แหล่งข้อมูล, `reach_id`, ลำดับบนลำน้ำ และระยะจากเขื่อนตามทางน้ำ พร้อมหลักฐานการจับคู่
- ตรวจด้วยแผนที่/เอกสารหน่วยงานเป็นรายเขื่อน โดยเริ่ม pilot 2–3 เขื่อนที่มีสถานีท้ายน้ำชัดเจน; ไม่ใช้การ snap จุดเข้ากับเส้นที่ใกล้ที่สุดแล้วถือว่าถูกต้อง
- เขื่อนที่จับคู่ไม่ได้ต้องแสดง “ยังไม่มีเส้นทางท้ายน้ำที่ตรวจสอบแล้ว” และรายงานจำนวนใน metadata

### 4.3 ข้อมูลการระบาย

- ยืนยันนิยามและหน่วยของ `inflow`/`outflow` จาก RID สำหรับแต่ละเขื่อน รวมถึงเวลาสิ้นสุดรอบรายงาน
- หาข้อมูลอัตราการระบายแบบ timestamped และประกาศแผนเพิ่ม/ลดการระบาย ถ้ามี API หรือเอกสารทางการ; อย่าทดแทนยอดรายวันด้วยค่าอัตรารายชั่วโมงที่อนุมานเอง
- บันทึกประวัติการระบายเพียงพอสำหรับคำนวณการเปลี่ยนแปลง โดยเก็บเวลา **วัด/รายงาน** แยกจากเวลาที่ backend ดึงข้อมูล

## 5. ลำดับงาน

### Phase 0 — ตรวจความเป็นไปได้ของข้อมูล

1. ตรวจ schema, หน่วย, ความถี่ และความครบของ `outflow` รายเขื่อนจาก RID อย่างน้อยหลายรอบอัปเดต
2. คัดเลือกแหล่งเส้นลำน้ำ พร้อมตรวจสิทธิ์ใช้และ attribution
3. เลือก pilot 2–3 เขื่อนที่มีเอกสารทางน้ำและสถานีท้ายน้ำตรวจสอบได้
4. ทำแผนที่ตัวอย่างเขื่อน → ช่วงลำน้ำ → จุดบรรจบ → สถานี; ให้ผู้รู้พื้นที่ตรวจ

**ผลส่งมอบ:** รายการแหล่งข้อมูล, ข้อจำกัดสิทธิ์, ตารางจับคู่ pilot พร้อมหลักฐาน, รายการช่องว่างที่ทำให้เผยแพร่ไม่ได้

**ประตูผ่าน:** อย่างน้อยหนึ่งเขื่อนมีทางน้ำต่อเนื่องและสถานีท้ายน้ำที่ตรวจสอบได้; หากไม่ผ่าน ให้หยุดฟีเจอร์อัตโนมัติและแสดงเฉพาะรายชื่อสถานีที่หน่วยงานระบุชัด

### Phase 1 — ไฮไลท์เส้นทางท้ายน้ำแบบเชิงโครงข่าย

1. จัดทำข้อมูลกราฟลำน้ำแบบ versioned และตารางจับคู่เขื่อน/สถานีที่ผ่าน review
2. เพิ่ม service อ่านกราฟและเดินตาม edge ท้ายน้ำ โดยหยุดที่ปลายทาง/ขอบเขตที่ตรวจสอบแล้ว และไม่เดินผ่าน edge `unknown`
3. เพิ่ม API แบบ read-only เช่น `GET /api/v1/dams/{dam_id}/downstream` ที่คืน GeoJSON เส้นทางและสถานี พร้อม `mapping_status`, `network_version`, provenance, `observed_at`, และรายการส่วนที่ไม่แน่ใจ
4. เมื่อเลือกเขื่อนใน dashboard แสดงเส้นประสีน้ำเงินและสถานีบนเส้นทาง พร้อมข้อความ “ลำน้ำท้ายน้ำที่เกี่ยวข้อง” เปิด/ปิดชั้นได้; ปิดเมื่อเลือกเขื่อนอื่นหรือยกเลิกการเลือก
5. แสดง `pending`/`unsupported` อย่างชัดเจน โดยไม่สร้างเส้นทางจากการประมาณระยะใกล้เคียง

**ประตูผ่าน:** เส้นทาง pilot ตรงกับแผนที่ที่ตรวจสอบแล้ว ไม่มีช่วงต้นน้ำหรือแม่น้ำข้างเคียงถูกไฮไลท์; ยังไม่มีสีเตือนภัยบนเส้น

### Phase 2 — เพิ่มสถานะเฝ้าติดตามจากหลักฐานจริง

1. เชื่อมค่าระบายล่าสุด/ก่อนหน้าและเวลารายงาน โดยใช้ cache ตามความถี่ต้นทาง
2. เชื่อมสถานีบนเส้นทางกับระดับน้ำและแนวโน้มจาก ThaiWater/DPM โดยใช้ logic จัดการสถานีซ้ำที่มีอยู่
3. ออกแบบเกณฑ์การเพิ่มระบาย **รายเขื่อน** จากข้อมูลย้อนหลังและคำแนะนำหน่วยงาน; เกณฑ์ยังไม่กำหนดตัวเลขกลางสำหรับทุกเขื่อน
4. แสดงสถานะแยกกัน: `ข้อมูลเส้นทาง`, `การระบายเพิ่ม`, `สถานีท้ายน้ำระดับสูง`, `ข้อมูลไม่พอ/เก่า`; ระบุเหตุผลและเวลาของแต่ละสถานะ
5. หากมีประกาศเพิ่มการระบายที่อ่านได้อย่างถูกต้อง ให้แนบข้อความและลิงก์แหล่งทางการ แยกประกาศจากค่าที่ระบบคำนวณ

**ประตูผ่าน:** สถานะทุกตัวตรวจย้อนกลับถึงข้อมูลต้นทางได้; missing/stale ไม่กลายเป็น “ปกติ”; การระบายสูงเพียงอย่างเดียวไม่สร้างข้อสรุปว่าน้ำท่วม

### Phase 3 — คาดการณ์ผลกระทบเฉพาะเมื่อมีข้อมูลและการสอบเทียบ

1. จัดหาข้อมูลการระบายแบบ time series, รูปตัดลำน้ำ, ภูมิประเทศ, แนวคัน/ประตูน้ำ, น้ำจากสาขา และข้อมูลสอบเทียบเหตุการณ์จริง
2. สร้าง/รับรองแบบจำลอง routing สำหรับเวลาและระดับน้ำท้ายน้ำ; ใช้ hydraulic model สำหรับแผนที่ระดับน้ำหรือพื้นที่ท่วม
3. สอบเทียบย้อนหลังหลายเหตุการณ์และประเมินความคลาดเคลื่อนของเวลา ระดับน้ำ และพื้นที่; ทบทวนโดยผู้เชี่ยวชาญก่อนแสดงต่อสาธารณะ
4. แสดงผลเป็น “คาดการณ์” พร้อมช่วงความไม่แน่นอน เวลาออกรุ่น และวันหมดอายุข้อมูล ไม่ปนกับการวัดจริง

**ประตูผ่าน:** มีเกณฑ์ความแม่นยำที่ตกลงกับผู้รับผิดชอบข้อมูลและผลทดสอบย้อนหลังผ่านเกณฑ์; มิฉะนั้นคง Phase 2

## 6. ข้อกำหนด API และข้อมูล

ตัวอย่างโครงสร้างเชิงแนวคิดของ endpoint Phase 1–2:

```json
{
  "dam_id": "<stable-rid-id>",
  "mapping_status": "verified",
  "network_version": "<version>",
  "reaches": {"type": "FeatureCollection", "features": []},
  "stations": [],
  "signals": {
    "storage": {"status": "very_high", "observed_at": null},
    "release": {"status": "unknown", "value": null, "unit": null, "observed_at": null},
    "downstream_gauges": {"status": "unknown", "observed_at_max": null}
  },
  "limitations": [],
  "sources": []
}
```

- ใช้ `dam_id` จากรหัสต้นทางเมื่อยืนยันความคงที่แล้ว; ชื่อเขื่อนเป็น label เท่านั้น
- API ต้องคืน topology version และ provenance เพื่อให้ตรวจย้อนหลังได้เมื่อเส้นทางเปลี่ยน
- ไม่ใส่ token หรือ key ลง GeoJSON หรือ frontend
- จำกัดจำนวน/ความยาวของเส้นทางตามขอบเขตที่ review แล้ว; bbox ใช้ลด payload ไม่ใช้กำหนดว่าทางน้ำจบตรงไหน
- ใช้การรายงานสถานะข้อมูลและ stale fallback ตามรูปแบบ API ปัจจุบัน แต่ข้อมูลเส้นทางกับข้อมูลสถานการณ์ต้องมีสถานะแยกกัน

## 7. การออกแบบบนแผนที่

- เส้นประสีน้ำเงิน = ความเชื่อมโยงทางน้ำที่ตรวจสอบแล้ว; ป้ายชื่อเขื่อนต้นทางและสถานีที่เชื่อม
- Badge “การระบายเพิ่ม” แสดงที่เขื่อน/แผงข้อมูล ไม่ระบายสีแดงทั้งลำน้ำ
- สถานีท้ายน้ำที่ถึงเกณฑ์ใช้สัญลักษณ์ระดับสถานีเดิม พร้อมข้อความ “ระดับน้ำสูงที่สถานีนี้”; แสดงเวลาอ่านค่า
- เมื่อข้อมูล stale ให้ลดความเด่นและแสดง “ข้อมูลล่าสุดเมื่อ…”; เมื่อ topology ไม่ผ่าน review ไม่วาดเส้น
- Legend ระบุความต่างระหว่าง “เส้นทางท้ายน้ำ”, “สถานีระดับน้ำสูง” และ “พื้นที่คาดการณ์” หากมีในอนาคต
- ปุ่มเลือกเขื่อนและ popup ต้องใช้ได้บนมือถือ คีย์บอร์ด และ screen reader

## 8. การตรวจรับและทดสอบ

| กรณี | ผลที่ต้องได้ |
|---|---|
| เขื่อนที่ตรวจสอบแล้ว | แสดงเฉพาะ reach ท้ายน้ำและสถานีที่ผูกไว้; ไม่ย้อนขึ้นต้นน้ำ |
| แม่น้ำแยก/บรรจบ | เดินตาม topology ที่ยืนยัน และหยุดที่ edge ที่ไม่แน่ใจ |
| คลองหรือประตูน้ำเปลี่ยนทิศได้ | ไม่ไฮไลท์ต่ออัตโนมัติโดยไม่มีสถานะการเดินระบบ |
| เขื่อน `% กักเก็บ` สูง แต่ไม่พบหลักฐานระบายเพิ่ม | แสดงสถานะกักเก็บและเส้นทางสีน้ำเงิน ไม่แสดงความเสี่ยงท้ายน้ำ |
| ระบายเพิ่ม แต่สถานีท้ายน้ำยังปกติ | แสดง “ควรติดตาม” และค่าจริง โดยไม่ใช้คำว่า “ท่วม” |
| สถานีท้ายน้ำสูง | แสดงระดับที่สถานีนั้นพร้อมเวลาและแหล่งข้อมูล ไม่สรุปว่าการระบายเป็นสาเหตุเดียว |
| ข้อมูล RID หรือสถานีหาย/เก่า | แสดง `unknown`/`stale`; ไม่สรุปว่าปลอดภัย |
| เขื่อนยังไม่จับคู่ | ไม่มีเส้นท้ายน้ำ; บอกเหตุผลและบันทึกใน metadata |
| โหลดเร็วหลายเขื่อนต่อเนื่อง | แสดงเส้นทางของเขื่อนที่เลือกล่าสุดเท่านั้น |

ก่อนเปิดใช้งานจริง ทดสอบเทียบเหตุการณ์ย้อนหลังและให้ผู้รู้พื้นที่ตรวจเส้นทาง pilot ทีละเขื่อน เก็บรายการข้อผิดพลาดที่พบและเวอร์ชันการแก้ไข

## 9. ความเสี่ยงและมาตรการ

| ความเสี่ยง | มาตรการ |
|---|---|
| จับคู่เขื่อนกับลำน้ำผิด | review รายเขื่อน, ใช้รหัสต้นทาง, เก็บ provenance, ไม่อนุมานจากระยะใกล้สุด |
| คลองหรือพื้นที่น้ำขึ้นลงมีการไหลย้อน | ทำเครื่องหมาย regulated/unknown และไม่เดินกราฟต่ออัตโนมัติ |
| รายงานการระบายเป็นยอดรายวัน | แสดงความถี่จริง; ไม่สร้างเวลาเดินทางหรืออัตรารายชั่วโมงเทียม |
| ฝนสาขาและเขื่อนอื่นทำให้ระดับน้ำสูง | แสดงสัญญาณหลายแหล่ง และหลีกเลี่ยงข้อความระบุสาเหตุเด็ดขาด |
| สถานีเสียหรือข้อมูลเก่า | ตรวจ observed time ต่อ request และแสดงสถานะข้อมูลชัดเจน |
| ผู้ใช้เข้าใจเส้นเป็นพื้นที่น้ำท่วม | ใช้เส้นประสีน้ำเงิน, คำอธิบายและ legend, ไม่ใช้ polygon หรือสีแดงโดยไม่มีแบบจำลอง |

## 10. ลำดับไฟล์เมื่อเริ่มพัฒนา

1. ข้อมูลกราฟลำน้ำและตารางจับคู่แบบ versioned ภายใต้ `backend/app/data/` พร้อมบันทึกแหล่ง/สิทธิ์
2. Service สำหรับ topology, station mapping และ signals ภายใต้ `backend/app/services/`
3. Endpoint และ metadata ใน `backend/app/api/routes.py`; TTL ใน `backend/app/config.py`
4. ชั้นเส้นทางและแผงอธิบายใน `frontend/app.js`, `frontend/index.html`, `frontend/styles.css`
5. Tests สำหรับ topology, stale/unknown, API contract และการเลือกเขื่อนหลายครั้ง
6. อัปเดต `README.md` และคำอธิบายข้อจำกัดของข้อมูล
